# 4주차 — 본실험 24 run 실행

**과제:** 검색 계산으로 통신량을 되사기 — 연합 LLM 미세조정에서 클라이언트 측
재순위의 환율

**범위:** Subtask 1.3 — 고정 통신 예산에서의 본실험, 그리고 **축이 하나만
변했는지에 대한 사후 검증.**

**이 보고서에서 다루지 않는 것:** 환율, 손익분기 곡면, 기전 점검은 Subtask 1.4
이며 별도로 보고한다. 본 보고서는 *무엇을 측정했고 그것이 깨끗하게 측정되었는지*
를 확립하며, **깊이 간 차이를 해석하지 않는다.**

---

## 1. 4주차의 산출물

완결된 연합학습 24회 — 재순위 깊이 6개 × 시드 4개 — 각각 동일한 통신 예산을
소모하며 early stopping 은 없다.

| | |
|---|---|
| run | **24 / 24 완료**, 실패 0 |
| 소요 시간 | NVIDIA A10G 1 대에서 **33.9 시간**, run 당 84.7 분 |
| run 당 라운드 | 59 |
| 라운드당 클라이언트 | 8 |
| 라운드당 로컬 스텝 | 32 |
| run 당 통신량 | **1,739,980,800 바이트 (1.7400 GB)** |
| 총 통신량 | 41.8 GB |
| 곡선당 평가 지점 | 21 (라운드 0 + 예약된 20) |

run 1 회는 59 × 8 = 472 회의 클라이언트 학습이므로, 스윕 전체는 11,328 회다.

### 깊이 사다리가 6 단인 이유

1–3주차를 작성할 때 사다리는 `{0, 3, 10, 50}` 네 단이었다. 지도교수의 제안에 따라
**중간 깊이를 보강**했고 — *"7, 20, 30 (또는 7 과 25)"* 두 안 중 후자를 택해 —
최종 사다리는 `{0, 3, 7, 10, 25, 50}` 이다. 간격은 2.33 / 1.43 / 2.5 / 2.0 배로
로그 축에서 고르며, 재순위 비용이 깊이에 비례하므로 추세는 그 축에서 읽어야 한다.

`5` · `20` · `30` 도 한때 설정에 들어 있었으나 측정하지 않았다. 이유는 3.1 절의
통제가 말해 준다: `d` = 3 은 프롬프트 내용을 바꾸지 않는데도 `d` = 0 과 **0.31 F1**
차이가 나고, 측정된 처리 효과는 전부 그 크기 이내다. 사다리를 촘촘히 해도 눈금보다
작은 양을 읽지 못하는 것은 같다. 시드로 그 간격을 메우려면 **16 개(64 run, 90 시간)**
가 필요하다.

시드는 4 개를 유지했다. 두 토픽 분할에 **번갈아** 배정되므로 시드 수가 짝수일 때만
두 분할이 균등하게 쓰인다 — 6 × 4 는 분할마다 12 run 이다.

| 시드 | depth 별 파티션 배분 | 6 depth 기준 run | 실측 84.7 분/run |
|---|---|---|---|
| 3 | 2 : 1 — 불균형 | 18 | 25.4 시간 |
| **4** | **2 : 2 — 균형** | **24** | **33.9 시간** |
| 5 | 3 : 2 — 불균형 | 30 | 42.4 시간 |
| 6 | 3 : 3 — 균형 | 36 | 50.8 시간 |

1 차 산출물은 24 개의 학습 곡선 `results/logs/runs/*.jsonl`, 868 KB 이며
버전관리된다. Subtask 1.4 분석이 읽는 **유일한 입력**이다.

## 2. 실행

### 2.1 실행 순서는 설계상의 결정이다

run 은 **seed 바깥 / depth 안쪽** 순서로 돌린다. 그래야 중간에 멈춰도 완료된
시드에 대해서는 네 조건이 모두 갖춰진다. depth 를 바깥에 두면 기준선 4 개만 있고
비교할 대상이 없는 상태가 된다.

### 2.2 동시 실행과 재개

스윕은 한 번에 하나만 돈다. 두 프로세스는 같은 곡선 파일에 라운드를 섞어 쓰고
GPU 에 모델을 두 벌 올린다. pid 락이 두 번째를 거부한다. 재실행되는 run 은 로그를
**새로 열며** 이어 붙이지 않으므로, 실패한 시도가 라운드를 되돌아가는 곡선을
남길 수 없다.

## 3. 축이 하나만 변했는지에 대한 검증

스윕 후 `scripts/check_runs.py` 가 24 run 의 모든 예산 필드를 비교하고 처리
진단을 확인한다. 기록된 결과:

```json
"runs_expected": 24,  "runs_complete": 24,
"identical_budget": true,  "issues": [],
"total_bytes": [1739980800],
"problems": []
```

`total_bytes` 는 **집합**이고 원소가 하나다. 라운드 수, 클라이언트 수, payload
크기, 라운드당 로컬 스텝, 옵티마이저 설정을 같은 방식으로 비교하며, 평가
스케줄도 비교한다. **일부 run 에만 기록된 필드 자체를 issue 로
보고**하므로, 필드가 생기기 전에 돌린 run 이 조용히 통과할 수 없다.

### 3.1 처리가 걸렸고, 통제가 유지되었다 — 그리고 그 수치가 말하는 것

`promotion_rate` 는 프롬프트에 들어간 3 개 passage 중 dense 검색이라면 고르지
않았을 비율이고, `rank_change_rate` 는 같은 자리의 passage 가 dense 상위 3 개와
다른 비율이다. 전자는 **내용**이 바뀐 정도, 후자는 **배치**가 바뀐 정도다.

| 깊이 | `rank_change_rate` | `promotion_rate` | 읽는 법 |
|---|---|---|---|
| 0 | 0.000 | **0.0000** | 아무 일도 없음 |
| **3** | **0.449** | **0.0000** | **같은 3 개, 다른 순서** |
| 7 | 0.648 | 0.3619 | 새 passage 승격 |
| 10 | 0.677 | 0.4202 | |
| 25 | 0.714 | 0.4976 | |
| 50 | 0.725 | **0.5252** | 가장 많이 승격 |

세 조건을 모두 통과했다: 통제군(`d` = 0, 3)은 아무것도 승격하지 않았고, 처리군은
승격했으며, 비율이 깊이에 대해 단조다. 여기까지는 장치가 작동했다는 확인이다.
그 다음이 이 수치가 말하는 것이다.

**(i) `promotion_rate` 는 처리의 "용량" 이며, 깊이에 대해 포화한다.** 승격률은
단조 증가하지만 증가폭이 급격히 줄어든다. 깊이 1 단위가 사오는 승격량으로 보면:

| 깊이 | `promotion_rate` | 깊이 1 당 승격 |
|---|---|---|
| 7 | 0.3619 | **0.0517** |
| 10 | 0.4202 | 0.0420 |
| 25 | 0.4976 | 0.0199 |
| 50 | 0.5252 | **0.0105** |

`d` = 7 에서 50 으로 가며 효율이 **4.9 배** 떨어진다. 깊이를 10 에서 50 으로
다섯 배 올려도 승격률은 0.420 에서 0.525 로 **25 % 만** 오른다. 교차인코더가
올릴 만한 passage 는 **후보 풀의 앞쪽에 몰려 있고**, 뒤쪽 후보를 추가로
재채점하는 것은 대부분 헛일이다. 수확 체감은 성능이 아니라 **여기서** 나타난다.

**(ii) 두 비율의 간격이 "재배열" 과 "교체" 를 가른다.** `d` = 7 에서 자리의
64.8 % 가 바뀌지만 그중 새 passage 는 36.2 % 뿐이다. 차이인 28.6 %p 는 **원래
있던 세 개를 섞은 것**이다. 깊이가 깊어질수록 이 간격은 좁아진다(`d` = 50 에서
72.5 % 대 52.5 %, 20.0 %p). 즉 얕은 깊이의 처리는 상당 부분이 순서 바꾸기이고,
깊은 깊이에서야 내용 교체가 주가 된다. `d` = 3 을 통제로 둔 이유가 이것이다 —
그 "순서 바꾸기" 성분을 따로 측정할 수 있어야 한다.

**(iii) `d` = 3 은 통제이면서 동시에 이 측정의 잡음 자를 준다.** `d` = 3 은
dense 가 이미 고른 세 개를 재채점하므로 **네 번째를 올릴 수 없고**, 승격률이
정의상 0 이다. 프롬프트의 내용이 `d` = 0 과 완전히 같다. 따라서 두 조건의 성적
차이는 **검색 품질과 무관한 변동**일 수밖에 없다. 실측값은 **+0.31 F1**
(± 0.37) 이다. 이 값은 4 절의 모든 깊이 간 비교를 읽는 기준이 된다. 어떤 처리
효과든 0.31 근처라면, 그것은 아무것도 바꾸지 않았을 때 생기는 크기와 같다.

### 3.2 평가 컨텍스트가 전 조건에서 동일했다 — 그리고 왜 그래야 하는가

평가는 전 조건 `d` = 0 에서 수행한다. 최종 라운드에서 평가 프롬프트 3 자리의
gold recall 은:

| 깊이 | 시드 1–4 |
|---|---|
| 0 | 0.497, 0.494, 0.497, 0.494 |
| 3 | 0.497, 0.494, 0.497, 0.494 |
| 7 | 0.497, 0.494, 0.497, 0.494 |
| 10 | 0.497, 0.494, 0.497, 0.494 |
| 25 | 0.497, 0.494, 0.497, 0.494 |
| 50 | 0.497, 0.494, 0.497, 0.494 |

깊이에 무관하게 소수점 셋째 자리까지 동일하고, 파티션 시드에 따라서만 달라진다.
**모든 조건이 같은 컨텍스트로 채점되었다.**

**왜 고정해야 하는가.** 재순위가 점수를 올릴 수 있는 경로는 둘이고, 둘은 전혀
다른 것이다.

| 경로 | 작동 방식 | 통신량과의 관계 |
|---|---|---|
| **학습 경로** | 더 좋은 passage 로 학습 → 더 좋은 기울기 → 더 좋은 가중치 | **있음.** 가중치가 좋아지면 목표에 더 적은 라운드로 도달하고, 라운드가 곧 바이트다 |
| **서빙 경로** | 추론 시점에 더 좋은 passage 를 받음 → 같은 가중치로 더 나은 답 | **없음.** 모든 질의마다 재순위를 영원히 돌려야 하고, 라운드 수와 무관하다 |

평가를 각 run 자기 깊이에서 하면 두 경로가 **더해져서 분리되지 않는다.**
`d` = 50 run 이 높은 점수를 받으면, 그것이 가중치가 좋아져서인지 시험 때 더 좋은
문서를 받아서인지 말할 수 없다. 그리고 서빙 경로는 거의 확실히 점수를 올린다 —
Week 2 에서 `d` = 50 의 gold recall 이 `d` = 0 보다 3.92 %p 높았다. 그 이득을
섞어 넣으면 "재순위가 통신량을 줄인다" 는 결론이 나오지만, 실제로 줄인 것은
아무것도 없다.

**고정의 대가.** 보고되는 F1 은 실제로 `d` = 50 으로 배치한 시스템이 낼 점수보다
낮다. 의도된 것이다. 이 실험이 묻는 것은 *최선의 서빙 구성이 몇 점인가* 가 아니라
*같은 통신 예산이 조건별로 무엇을 사주는가* 이기 때문이다. 서빙 이득은 Subtask
1.4 의 비용 모델에서 **FLOPs 지출로 따로** 회계된다 — 공짜가 아니라 값이 매겨진다.

## 4. 기록된 결과

### F1 과 EM 이 재는 것

둘 다 모델이 생성한 답을 정답과 대조해 채점하며, Natural Questions 공식 정규화를
먼저 적용한다 — 소문자화, 구두점 제거, 관사(*a*, *an*, *the*) 제거, 공백 정리.

**EM(Exact Match)** 은 정규화 후 문자열이 같으면 1, 아니면 0 이다.
**Answer F1** 은 토큰 겹침이다: 모델이 말한 것 중 정답에 있는 비율과, 정답 중
모델이 말한 비율의 조화평균이다. 정답이 여러 개인 질문에서는 가장 높은 점수를 쓴다.

| 모델의 답 | 정답 | F1 | EM |
|---|---|---|---|
| `The Barack Obama` | Barack Obama | **1.000** | **1** |
| `Barack Hussein Obama` | Barack Obama | **0.800** | 0 |
| `Obama` | Barack Obama | **0.667** | 0 |
| `Donald Trump` | Barack Obama | 0.000 | 0 |

`Barack Hussein Obama` 는 세 토큰 중 둘이 두 토큰짜리 정답과 겹치므로 정밀도
2/3, 재현율 2/2 이고 F1 은 0.800 인 반면 EM 은 0 이다. 둘 다 관례대로 0–100
스케일로 보고하므로, F1 29.13 은 질문별 F1 의 평균이 0.2913 이라는 뜻이고
EM 22.32 는 1,000 질문 중 22.32 % 를 정확히 맞혔다는 뜻이다.

F1 이 주 지표인 이유는 **연속값이라 보간이 안정적**이기 때문이다. EM 은 계단
함수여서 목표 도달 라운드 추정을 튀게 만든다. EM 을 함께 기록하는 이유는, F1 만
보면 *"토큰이 우연히 겹쳐서 점수가 올랐다"* 는 반론이 가능하기 때문이다 — EM 이
같이 움직이면 모델이 **근접한 것이 아니라 실제로 맞히게 되었다**는 뜻이다. EM 이
F1 을 넘을 수는 없다: 정확히 맞으면 F1 도 1 이다.

### 4.1 깊이 ↔ 계산비용 ↔ 성능 ↔ 통신량

| `d` | 쿼리당 FLOPs | 쿼리당 초 | `promotion` | F1 (평균 ± s.e.) | **vs `d` = 0** | **vs `d` = 3 (통제)** |
|---|---|---|---|---|---|---|
| **0** | 0 | 0.000 | 0.0000 | 29.13 ± 0.69 | — | −0.31 ± 0.37 |
| **3** | 1.63 × 10¹⁰ | 0.147 | 0.0000 | 29.44 ± 0.76 | **+0.31 ± 0.37** | — |
| **7** | 3.81 × 10¹⁰ | 0.344 | 0.3619 | 29.20 ± 0.76 | +0.07 ± 0.16 | **−0.24 ± 0.27** |
| **10** | 5.44 × 10¹⁰ | 0.492 | 0.4202 | 29.72 ± 0.55 | +0.60 ± 0.28 | +0.29 ± 0.25 |
| **25** | 1.36 × 10¹¹ | 1.229 | 0.4976 | 29.24 ± 0.39 | +0.11 ± 0.47 | **−0.20 ± 0.42** |
| **50** | 2.72 × 10¹¹ | 2.458 | 0.5252 | 29.41 ± 0.48 | +0.28 ± 0.31 | **−0.03 ± 0.45** |

비교는 **같은 시드 안에서 쌍체**로 한다. 시드 간 변동이 깊이 간 차이보다 크기
때문이다 — 기준선만 해도 27.89 에서 30.66 까지 2.77 F1 의 폭을 가지는데, 깊이
간 차이는 1 F1 미만이다. 쌍체로 보면 그 폭이 상쇄된다.

통신량 쪽은 설계상 **전 조건이 동일한 1.7400 GB** 를 썼다. 따라서 절약은 *같은
목표에 더 적은 라운드로 도달하는 것* 으로만 발생할 수 있다.

목표 점수 τ 는 **고르지 않는다.** τ 를 하나 고르면 결론이 그 선택의 산물이 되므로,
기준선(`d` = 0) 네 run 이 실제로 기록한 80 개 평가 점수 중 비교가 성립하는 구간
안의 **63 개를 전부** 목표로 삼는다. 구간의 두 경계도 유도된다 — 아래는 기준선이
라운드 1 에 이미 넘은 점수의 최댓값(18.13), 위는 기준선 최고점의 최솟값(28.14)이다.
그보다 낮으면 전 조건이 1 라운드에 도달하고, 높으면 도달하지 못하는 시드가 생긴다.

각 목표마다 깊이별 도달 라운드를 시드 4 개에서 보간해 평균하고, 기준선과의 차이를
구한다. 63 개 목표 전체의 요약:

| `d` | 기준선보다 빨랐던 목표 | 그중 오차를 넘는 것 | 절약 라운드 (중앙값) | 범위 |
|---|---|---|---|---|
| **3** *(통제)* | **41 / 63** | **26 / 63** | **+0.149** | −0.88 ~ +11.35 |
| 7 | 19 / 63 | 10 / 63 | −0.560 | −5.46 ~ +4.84 |
| 10 | 20 / 63 | 16 / 63 | −0.213 | −2.47 ~ +8.16 |
| 25 | 24 / 63 | 9 / 63 | −0.113 | −1.86 ~ +3.14 |
| 50 | 15 / 63 | 7 / 63 | −0.374 | −5.75 ~ +3.91 |

평균이 아니라 **중앙값**이고, 절약의 크기가 아니라 **목표의 개수**를 세는 이유는
같다. τ 가 높아질수록 기준선 곡선이 평평해져(τ = 25.02 에서 9.0 라운드, τ = 28.14
에서 38.7 라운드) F1 0.1 점 차이가 라운드 10 개로 번역되고, 절약이 ±11 까지 튄다.
그 구간을 **잘라내지는 않았다** — 어디서 자를지가 또 하나의 임의 선택이 되기
때문이다. 대신 크기가 지배하지 못하는 통계로 읽는다.

"오차를 넘는 것" 은 절약이 자기 표준오차보다 큰 목표의 수다. 시드 4 개에서 잰
값이므로 측정 자체가 ±0.2 ~ ±0.9 라운드 흔들리고, 그보다 작은 절약은 이겼다고
말할 수 없다.

### 4.2 세 가지 물음에 대한 답

**(a) 깊이를 올리면 성능이 일관되게 좋아지는가 — 아니다.**

위 표에서 `d` = 0 대비 이득은 +0.07 → +0.60 → +0.11 → +0.28 로 **단조가 아니고**,
전부 자기 표준오차 안에 있다. 더 결정적인 것은 **통제 대비** 열이다. `d` = 3 은
프롬프트 내용을 바꿀 수 없는데도 `d` = 0 보다 **+0.31** 높다. 통제 대비로 다시
읽으면 네 처리 중 **셋이 음수**다(−0.24, −0.20, −0.03). `d` = 10 의 +0.60 도 절반
이상이 통제와 공유되는 성분이며, 통제 대비로는 +0.29 ± 0.25 로 줄어든다.

> 승격률은 0 → 0.525 로 **깨끗하게 단조**인데 성능은 따라오지 않는다. 처리 용량은
> 분명히 커졌고, 그 용량이 학습 결과로 옮겨가지 않았다.

**(b) 수확 체감은 어디서 나타나는가 — 성능이 아니라 승격률에서.**

성능에는 체감할 이득 자체가 없다. 체감이 보이는 곳은 3.1 절의 승격률이다: 깊이
1 단위가 사오는 승격량이 `d` = 7 의 0.0517 에서 `d` = 50 의 0.0105 로 **4.9 배**
떨어진다. 비용은 깊이에 비례해 선형으로 늘어나므로(쿼리당 0.344 초 → 2.458 초,
**7.1 배**), 깊이를 올릴수록 **비용은 선형으로 늘고 처리 용량은 포화한다.**
꺾이는 지점은 `d` = 10 과 `d` = 25 사이다.

**(c) 어느 깊이가 최선의 절충인가 — `d` = 0.**

모든 깊이가 쿼리당 FLOPs 를 지출하고, 측정 가능한 성능도 통신량도 사지 못한다.
`d` = 50 은 쿼리마다 2.72 × 10¹¹ FLOPs(이 CPU 에서 2.46 초)를 쓰면서, 63 개 목표
중 15 개에서만 기준선보다 빨랐고 중앙값은 **0.374 라운드 느림**이다. 네 처리의
중앙값이 모두 음수다.

가장 결정적인 것은 **통제가 1 위라는 사실**이다. `d` = 3 은 프롬프트 내용을 바꿀
수 없는데 63 개 목표 중 **41 개**에서 기준선보다 빨랐고, 오차를 넘는 경우도
**26 개**로 네 처리를 모두 앞선다. 아무것도 바꾸지 않은 조건이 가장 자주 이긴다면,
그 승패는 처리의 효과가 아니라 **측정의 변동**이다.

Subtask 1.4 의 기전 점검도 같은 판정을 낸다: *가장 큰 중앙값 절약은 `d` = 3 의
+0.149 라운드이고, 63 개 목표 중 26 개에서만 자기 표준오차를 넘는다. 어떤 깊이도
과반의 목표에서 절약을 분해하지 못한다.*

### 4.3 이 결과를 어떻게 읽어야 하는가

음성 결과이지만 **실패한 측정이 아니다.** 사슬의 어느 고리가 끊겼는지가 특정된다.

| 고리 | 측정값 | 상태 |
|---|---|---|
| 깊이 → 검색 품질 | 2 주차 gold recall +3.92 %p, 승격률 0 → 0.525 | ✅ **작동** |
| 검색 품질 → 학습 입력 | 프롬프트의 52.5 % 가 dense 가 못 고른 passage | ✅ **작동** |
| **학습 입력 → 학습 결과** | **F1 차이가 전부 잡음 바닥(0.31) 안** | ❌ **끊김** |
| 학습 결과 → 라운드 절약 | 측정할 대상 없음 | — |

끊긴 자리는 **세 번째 고리**다. 더 좋은 passage 가 프롬프트에 분명히 들어갔는데,
이 모델 규모(135M)와 이 예산(59 라운드, 1.74 GB)에서 그것이 가중치의 차이로
나타나지 않는다. 7 절의 한계와 함께 읽어야 할 결론이다 — 이 결과는 "재순위가
쓸모없다" 가 아니라 "이 조건에서는 재순위가 통신량을 되사지 못한다" 이다.

## 5. 두 분할의 질문 수가 다른 이유

결과 표는 각 run 이 어느 토픽 배분을 썼는지 기록한다. 두 분할은 클라이언트당
9,844 개와 9,742 개를 가지며 102 개, 1.0 % 차이다. 언뜻 불일치로 보이므로 과정을
밝혀 둔다.

**1 단계 — 질문을 주제별로 묶는다.** 파티션 시드는 k-means 클러스터링의
`random_state` 다. 시드가 다르면 클러스터가 다르게 잘린다 — 어떤 passage 들이 한
덩어리가 되는지가 달라진다.

**2 단계 — 클러스터를 클라이언트 8 개에 나눠준다.** 클러스터는 크기가 제각각이라
클라이언트가 고르게 나뉘지 않는다. 절삭하지 않은 passage 수가 그 불균등을 보여준다:

| 시드 | 클라이언트별 passage | 편차 |
|---|---|---|
| 1001 | 26219, 26870, 25404, 23942, 25058, 22026, 25331, 25150 | 22,026–26,870, **22 %** |
| 1002 | 25695, 28164, 24899, 23411, 22710, 26977, 23100, 25044 | 22,710–28,164, **24 %** |

질문 수도 같은 식으로 들쭉날쭉하게 나온다.

**3 단계 — 모든 클라이언트를 가장 적은 쪽에 맞춰 자른다.** 균등은 여덟 개를 전부
가장 적게 배정받은 클라이언트의 크기로 잘라 강제한다. 따라서 공통 크기는 **가장
작은 클라이언트가 가진 수**이고, 그것은 클러스터링이 어떻게 나왔느냐가 정한다.

**4 단계 — 그 "가장 작은 클라이언트" 가 시드마다 다르다.** 1001 에서 9,844,
1002 에서 9,742 다. 절삭으로 첫 분할에서 1,968 개(2.4 %), 두 번째에서 2,784 개
(3.4 %)가 버려진다.

절삭은 의도된 것이다. 클라이언트 크기가 다르면 FedAvg 평균이 불안정해진다 —
데이터가 많은 클라이언트가 평균을 더 끌어당기기 때문이고, 그 불안정성이 depth 와
나란히 **두 번째 변동 요인**으로 작용한다. 질문 2,784 개를 버리는 대가로
`question_size_spread: 0` 을 얻는다.

분할 간 1.0 % 차이는 depth 비교에 도달하지 않는다. 같은 시드를 쓰는 run 은 같은
분할을 쓰고 비교는 **같은 시드 안에서** 이루어지므로, 그 값이 뺄셈의 양쪽에 똑같이
들어가 상쇄된다.

## 6. Subtask 1.4 를 위해 측정한 비용 모델 입력

`scripts/measure_flops.py` 가 비용 모델이 청구하는 쌍당 재순위 비용을 확정한다.
수치를 쓰기 전에 **오류 두 개를 찾아 고쳤다.**

추정식은 `2 × params × tokens` 를 재순위 모델의 전체 22,713,601 파라미터에
적용했으나, 그중 11,917,824 개(**52 %**)가 임베딩 행렬이며 gather 로 읽히고
행렬곱에 들어가지 않는다. 2.1 배 과대계상이다. 한편 실측은 패딩 없이 **66 토큰**
으로 토큰화되는 샘플에서 수행되었는데 추정식은 **256 토큰**을 가정하므로 3.9 배
과소계상이다. 두 값이 8.7 배 벌어진 상태에서 코드가 조용히 실측 쪽을 선택했다.

| | 수정 전 | 수정 후 |
|---|---|---|
| 추정식, 쌍당 | 1.223e10 | **6.131e9** |
| 실측, 쌍당 | 1.402e9 (66 토큰) | **5.437e9 (256 토큰)** |
| 일치도 | 8.7 배 차이 | **11 % 차이** |

파라미터 수에서 임베딩을 제외했고, 측정은 추정식이 가정하는 토큰 수로 패딩하며,
두 토큰 수를 모두 기록하고, 2 배 이상 벌어지면 경고를 남긴다. 남은 11 % 는
profiler 가 layernorm·softmax·elementwise 연산을 세지 않는 몫이다.

가정하지 않고 확인한 것: `torch.profiler` 의 `with_flops` 는 행렬곱에 대해
2 × MAC 을 보고하므로 이미 FLOPs 기준이고 2 배 보정은 해당되지 않는다.

**처리량 수치는 쓸 수 없다.** 워밍업 없이 forward 한 번을 장치 동기화 없이
쟀다. CUDA 는 비동기로 큐에 넣으므로 호출이 계산 완료 전에 돌아오고, 그 한 번에
host-to-device 전송과 커널 컴파일까지 섞인다. A10G 에서 81 쌍/초, 노트북 CPU 에서
84 쌍/초가 나왔는데, **GPU 가 CPU 보다 낮게 읽히면 그것은 결과가 아니라 측정
오류다.** 측정은 이제 워밍업·반복·동기화를 하고 배치 크기, 반복 횟수, 쌍당 토큰
수를 기록하지만, 수치 자체는 대상 장치에서 재측정해야 한다.

## 7. 이번 주 자료에서 드러난 한계

마지막에 발견하는 것이 아니라 여기에 적는다.

**곡선이 수렴하지 않았다.** 24 개 중 대부분이 라운드 50 이후에 최고점을 가지며,
학습 손실은 라운드 59 에서도 내려가는 중이었다. 이 예산 바깥의 거동은 관측되지
않았고, 기준선이 도달한 값보다 높은 목표 정확도는 외삽 없이는 보고할 수 없다.

**곡선이 단조가 아니다.** 학습 후반에 연속 평가 라운드 사이에서 held-out F1 이
최대 1.38 F1 까지 떨어지는데 그 구간에서 학습 손실은 계속 내려간다. 따라서 그
하강은 과적합이 아니라 **평가 노이즈**다. 클라이언트 데이터를 1.53 바퀴 도는
설정에서 과적합이 나오는 것도 기대하기 어렵다.

**네 깊이 중 셋은 강제되고 `d = 10` 은 아니다.** `d = 0` 은 기준선, `d = 3` 은
순서 통제가 성립하려면 `top_k` 와 같아야 하며, `d = 50` 은 후보 풀 전체다.
내부 점은 3 과 50 사이에 대략 등비로 놓았고 **유도되지 않았다.**

**후보 풀 50 은 선언된 거래다.** 게이트 2 가 천장을 풀 50 에서 0.669, 100 에서
0.721, 200 에서 0.774 로 측정했다. 풀을 키우면 천장이 올라가지만 재순위 FLOPs 가
비례해 늘고, 그 FLOPs 가 환율의 비용 쪽이다.

**모델 규모와 어댑터 rank 는 하나씩이다.** SmolLM2-135M, attention projection 에
LoRA rank 8, 학습 파라미터 921,610 개. 시드 4 개이므로 효과 크기와 표준오차를
보고하며 유의성 검정은 주장하지 않는다.

## 8. 현황

Subtask 1.3 은 완료되었다. 24 개 곡선이 존재하고, 동일한 예산으로 구매되었으며,
**예산의 동일성과 처리의 발생이 모두 주장이 아니라 로그로부터 검증**되었다.
Subtask 1.4 가 그 곡선을 읽는다.
